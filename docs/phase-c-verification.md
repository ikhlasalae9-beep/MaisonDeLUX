# Phase C — architecture, verification and rollout limits

## Architecture

- One identity stack: Supabase Auth through server-only `@supabase/ssr`, verified `getUser()` identities, PKCE email callbacks, HttpOnly / SameSite=Lax session cookies (Secure in production). No credentials in public application tables. Private responses are no-store; redirects accept same-locale internal paths or the exact server-guarded `/admin` path.
- Additive migrations 004/005 introduce profiles, separate roles, saved properties, guest trials, security audit logs, prediction/context snapshots and durable rate-limit counters. The only V2 event-schema addition is nullable `user_id → auth.users`, ON DELETE SET NULL. Global analytics retain their trusted server-side SQL and unchanged methodology.
- RLS permits own profile reads/allowed updates, own property CRUD, own history/passport reads and own role reads. Clients cannot mutate roles or events, access guest/audit/limiter tables, or execute entitlement/claim functions. New users always receive `user`, even with forged role metadata. Definer functions use an empty explicit search path.
- Main estimation: validate → verify session/guest → durable limit → check replay → reserve guest entitlement → signed request to the **unchanged** Casablanca pipeline → atomically store event + snapshot + consumed trial. Failed inference releases its lease and consumes nothing. If optional persistence fails after a valid model response, the real prediction is returned without an event ID and the reservation is released. The browser retains the request ID across failed retries of the same input so a committed response can be replayed without re-running the model. Browser-authored analytics writes are closed (410); only server-completed predictions create main events.
- During the narrow rollout window where the Phase C guest secret or database objects are absent, estimation uses a logged compatibility path: the signed official model prediction (and best-effort context) remains available, while guest enforcement, persistence, claim, history and simulations are explicitly unavailable. Apply migrations 004/005 and configure the guest secret to activate those features. This is availability degradation, not fabricated data.
- The raw 256-bit guest token exists only in an HttpOnly cookie. PostgreSQL stores purpose-separated HMACs, not raw IP, user agent or token. Default window: 30 days. Device-ish heuristic: IPv4 /24 or IPv6 /64 prefix + OS family + desktop/mobile + primary language, ignoring browser brand. Daily network cap: 8, not one user per IP. Same-network reservations are serialized with advisory/row locks, with a 120-second lease exceeding the 55-second model request timeout.
- Simulations and optional context require ownership of the parent event. What-if can alter only the existing supported surface/floor/condition/age scenario fields; it never calls main-event completion or consumes another trial. Rate limits apply separately. Main authenticated predictions have no product count limit.
- Claim: server hashes the current HttpOnly cookie, then a locked SQL transaction follows that guest row's event link. No event/user ID is accepted from the browser for claim. Repetition by the same owner is idempotent; a different owner is refused. Login, callback and account entry retry the claim. Claims require an unexpired guest token.
- Account dashboard, paginated history, historical Passeport, saved-property save/rename/delete/prefill, factual 2–6 item comparison and security/logout pages are localized. Historical prices are snapshots, not recalculated predictions. Configurations without a saved prediction show no fabricated price. Account UI is a separate route chunk, not loaded by Landing/City/Market.
- Every privileged Admin API and the page use server-side `requireAdmin()`. Supabase users need the database `admin` role. Legacy HMAC Admin cookies remain valid only in explicit compatibility mode pending manual bootstrap; they are not equivalent to arbitrary browser role metadata. The new security tab is read-only and displays aggregate counts/event types/timestamps, not credentials or IPs.
- New write routes use an Origin/Fetch-Metadata check, key allowlists, bounded streamed JSON (16 KiB), strict identifiers, parameterized SQL and safe error codes. The Python transport requires a timestamped body/path HMAC before model loading/invocation. Public metadata/Market remain accessible.

## Defaults and headers

| Operation | Default limit |
| --- | --- |
| Guest main | 6/minute per network, plus one discovery entitlement |
| Authenticated main | 30/minute per user |
| Guest what-if/context | 15/minute per token, separate action counters |
| User what-if/context | 60/minute per user, separate action counters |
| Login/signup/recovery/logout | 20/15 minutes per network and action |
| Property creation | 30/minute per user |

Thresholds used by estimation/auth are configurable through `.env.example`; counters live in PostgreSQL, not process memory. Legacy login retains its existing protection before Phase C configuration; it gains durable limiting once the secret/schema are configured. Complete the Admin transition before rollout.

CSP constrains resources, base URI, form actions, object loading and framing; compatible sources include existing AdSense and Unsplash. Existing Next hydration/theme code requires `unsafe-inline` for scripts/styles; `unsafe-eval` is development-only. Also set X-Frame-Options DENY, nosniff, strict-origin-when-cross-origin, camera/microphone/geolocation/payment restrictions, and production HSTS. This is **not** a nonce-based strict CSP. Browser inspection found no application/CSP console errors on checked auth pages; production ad delivery still needs a live check.

## Required live staging verification (not claimed as passed)

Use a staging database based on finalized V2 and the same migrations, two verified users A/B, one manually bootstrapped Admin, and independent server secrets. Never use production accounts/listings to automate destructive tests.

3. In a fresh guest browser/network test cohort, submit a valid main estimation. Confirm full price/Passeport/context/comparables and what-if remain visible without signup. Check one event/snapshot and one consumed guest trial in operator SQL; no raw token/IP is stored. Save the test event IDs for cleanup by an authorized operator.
4. Attempt a second main: expect `GUEST_TRIAL_CONSUMED`, the friendly account gate and zero new Python model invocation. Repeat after clearing localStorage/sessionStorage, in another browser/incognito with the same coarse signals, and after several hours: entitlement remains consumed. Changing network/OS/language can defeat the heuristic and is an acknowledged limitation, not a test failure of exact device identity.
5. On an unused guest identity, force one trusted backend prediction failure: no consumption/event. Restore the backend and retry successfully. Run two simultaneous main requests on separate worker connections (same token, then two tokens with same coarse signals): at most one prediction reservation wins. Force a worker interruption and verify retry only after lease expiry. Exhaust configured network cap without assuming one shared IP is one person.
6. Run repeated what-if calls for the existing passport: no new main rows/trial changes; supported changes use the same official model. 10. Request every `/api/admin/*` privileged read as guest and ordinary A: reject; request as the bootstrapped Admin: allow. ## Real limitations / release blockers

- **Dependency audit is not clean.** `npm audit --omit=dev` on 2026-09-26 reports two vulnerable production packages: existing Next.js 14.2.35 (critical) and its nested PostCSS (high). Not every advisory applies to this deployment, but this must not be labelled production-secure. In particular [Windows-hosted RCE](https://github.com/advisories/GHSA-p293-qw3h-jr36) and [AVIF image-optimizer RCE](https://github.com/advisories/GHSA-2xp9-vwfh-vxw4) identify patched 15.5.24+ branches in the audit. npm proposes a major framework upgrade; none was silently applied during Phase C. Perform a scoped supported-version migration and re-audit before release. Local verification is bound to loopback only.
- Existing shared `lib/admin/db.ts` uses encrypted PostgreSQL TLS with `rejectUnauthorized:false`. This legacy behavior was not silently changed because it could break the current Admin connection. It does **not authenticate the DB certificate** and must be remediated/tested with the actual Supabase CA before production Phase C. The manual bootstrap already requires verified TLS. `.env.example` documents the CA for bootstrap; the legacy shared pool does not yet consume it.
- The heuristic can falsely group people sharing network/OS/language and can be evaded by changing signals, proxy/network or device. It is privacy-preserving abuse mitigation, not identity proof. No fingerprinting or claim of perfect anti-abuse. Endpoint-level limits do not replace host/WAF limits or Supabase's direct Auth endpoint protections.
- Real email delivery, hosted Auth/JWT/RLS integration, multi-worker database locking, authenticated browser/account/Admin walkthrough and production ad behavior still require manual staging checks. Missing Phase C migrations/guest secret now preserve the signed base prediction through the logged compatibility path, but entitlement, persistence, claim, history and simulations remain unavailable until rollout is complete. Missing both inference-gateway and legacy Admin server secrets still fails closed. Snapshot/context availability depends on the actual backend; no fake substitutes exist.
- Legacy Admin compatibility is temporary; retire it after verified role bootstrap. CSP still allows existing inline scripts. Secret rotation and retention policies need operator decisions. No push, merge, deployment, production migration or model modification was performed.
