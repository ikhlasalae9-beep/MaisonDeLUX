# Phase C — manual setup only

Do not expose this checkout publicly yet. Resolve the dependency/TLS blockers in `phase-c-verification.md` and complete staging verification before any production rollout. No production migration, bootstrap or deployment was performed by this implementation.

1. In the **existing Supabase project → Authentication → Providers → Email**, enable email/password and **Confirm email**. Require at least 12 characters; configure production SMTP delivery and provider rate limits. Do not disable verification to work around delivery failures.
2. In **Authentication → URL Configuration**, set Site URL to `https://www.maison-delux.com`. Allow `http://localhost:3000/**` and `https://www.maison-delux.com/**`. Add only explicitly trusted staging origins when needed. The locale-specific callbacks are `/fr/auth/callback` and `/ar/auth/callback`. Recovery adds `?flow=recovery` and redirects to the matching `/auth/reset-password` page. Retain Supabase's `{{ .ConfirmationURL }}` email links, which complete verification and redirect with a PKCE code. Open the confirmation/reset link in the browser that started the flow; PKCE verifier cookies are required.
3. Back up the database and confirm migrations 001–003/finalized V2 are already present. In a staging copy first, review and run **004_phase_c_identity_rls.sql**, then **005_phase_c_entitlements.sql**, each once. Do not rerun historical cleanup migrations or recreate `estimation_events`. Confirm existing city/model/event counts are unchanged and the new nullable `user_id` leaves historical anonymous records valid. Review existing Supabase grants/policies alongside the restrictive owner policy.
4. Configure existing public Supabase URL and publishable/anon key under the names in `.env.example`. Keep `POSTGRES_URL` server-only. Configure the trusted Supabase CA where needed; never put a database/service-role credential in a `NEXT_PUBLIC_*` variable. Review verified TLS before rollout (see verification report).
5. Generate **two distinct** random secrets locally using a trusted secret manager, or run `node -e "console.log(require('node:crypto').randomBytes(32).toString('base64url'))"` separately for each. Store them only in deployment secret settings: `GUEST_TRIAL_HMAC_SECRET` (Next server) and `INFERENCE_GATEWAY_SECRET` (both Next and Python servers). Do not paste them into issues, this document, or version control. Use independent staging values. Rotation invalidates existing guest identities; plan it explicitly.
6. Set `SITE_URL=https://www.maison-delux.com` in production and `http://localhost:3000` locally. Set `ML_BACKEND_URL` only to the trusted Python service base URL if it is separate; local development defaults to `http://127.0.0.1:5000`. Coordinate Node and Python rollout: direct unsigned inference now fails closed. Do not deploy one side alone. Missing Phase C tables/secrets intentionally disable estimation/auth writes rather than granting free trials.
7. On Vercel, use its overwritten `x-vercel-forwarded-for` identity signal. On other hosts, configure a trusted reverse proxy to **overwrite**, not append/trust, a client IP header, then set `TRUSTED_CLIENT_IP_HEADER` to that header. Prevent direct access around that proxy. Do not set an arbitrary client-supplied header as trusted. Configure host-level request/body/connection limits as well as application limits.
8. Keep `ADMIN_AUTH_MODE=compatibility` while bootstrapping. Create and email-verify the administrator through the normal signup flow. Obtain that existing user's UUID from Supabase Auth. From a trusted operator terminal with privileged server-only database credentials and verified TLS, run `node scripts/bootstrap-admin.mjs <verified-user-UUID>`. This is a privileged, audited role assignment, not a public endpoint. Test the Supabase login link on `/admin/login`, all existing Admin views and **Utilisateurs & Sécurité**. Only then set `ADMIN_AUTH_MODE=supabase-only` and retire/rotate legacy Admin credentials and cookies. No administrator was bootstrapped automatically.
9. Complete the live two-user/guest/browser checklist in `phase-c-verification.md`. Configure privacy retention with an approved operator: prune expired limiter rows and expired guest records on a scheduled basis after the chosen recovery retention period, and define audit-log retention. Never delete active entitlements or analytical events as a shortcut. No retention/deletion job has been installed or run.
